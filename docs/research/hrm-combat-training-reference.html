Architecture review · experiment specification

Hierarchical Reasoning Models for combat

A source-grounded distillation of Sapient’s HRM, rewritten as a practical reference for training a model to solve complete Slay the Spire boss combats from engine checkpoints.

self-contained HTML official paper v3 official code @ ac15626 combat adaptation clearly labeled

Executive answer

Promising as a planner architecture, not a drop-in agent

HRM’s useful idea is recurrent latent computation at two timescales: a slowly changing state can represent the fight plan while a faster state resolves card order, targeting, energy, orbs, and immediate consequences. Its published training problem, however, is static supervised sequence-to-sequence prediction—not interactive game play or reinforcement learning.

HRM fact

What transfers

Coupled high/low recurrent states, repeated latent refinement, deep supervision, constant-memory approximate gradients, and optional adaptive inference compute.

Translation

What must change

Grid-token decoding becomes legal-action scoring. One static answer becomes repeated decisions against exact engine transitions. Puzzle identity becomes encounter context—not seed identity.

Combat proposal

First experiment

Behavior-clone the winning suffixes of 500 held-out-by-seed Act 3 boss-entry puzzles, then compare HRM against compute- and parameter-matched direct and single-recurrent baselines.

The 500 winner-only entries are sufficient for the scoped task. Each entry is a complete, multi-turn planning puzzle with a verified winning continuation. The task is to choose strong actions and make measurable progress from the supplied state; state classification is outside the objective.
Non-negotiable semantic boundary: HRM’s halt action means “stop internal computation and emit the current prediction.” It must never be mapped to the game’s EndTurn action.

HRM fact

What HRM actually computes

HRM has four learned transformations: input encoding fI, low-level recurrence fL, high-level recurrence fH, and output decoding fO. The two recurrent modules hold full sequence-shaped hidden states.

Input tokensx → fI(x)
Low state zLfast detail · updates T times per cycle
High state zHslow context · updates once per cycle
OutputfO(zH)
x̃ = fI(x)
zLᵢ = fL(zLᵢ₋₁, zHᵢ₋₁, x̃)
zHᵢ = fH(zHᵢ₋₁, zLᵢ₋₁)  when i mod T = 0; otherwise zH is held fixed
ŷ = fO(zHᴺᵀ)

A segment contains N high-level cycles and T low-level updates per cycle. The paper calls the resulting behavior hierarchical convergence: the low state settles under one high-level context, then the high state changes that context and starts another refinement phase. Effective recurrent depth is N × T per segment, multiplied again by the number of deep-supervision segments.

High module

Updates slowly after receiving the last low-level state for a cycle. The authors associate it with abstract planning, but the architecture does not force a human-readable plan into this state.

Low module

Updates repeatedly while the high state remains fixed. The authors associate it with detailed computation, but “search” and “backtracking” are interpretations of observed predictions—not explicit algorithms in the model.

Important epistemic limit: visualizations suggest exploration, pruning, and correction on maze/Sudoku tasks. They do not prove that HRM learned a discrete search algorithm or that the high and low states will spontaneously separate into strategy and tactics in combat.

One-step gradient approximation

Ordinary backpropagation through time stores the unrolled recurrence. HRM instead executes every recurrent update except the last low update and last high update under no_grad, then differentiates through those final two updates. Segment-to-segment carry is detached.

01EncodeEmbed all input tokens.
02Recur detachedRun early H/L cycles without an autograd history.
03Final L + HTrack gradients through one update of each module.
04DecodePredict output and halt/continue values.
05UpdateOptimize, detach carry, optionally continue.

The paper motivates this as the first term of a Neumann-series approximation to an implicit fixed-point gradient. It offers constant activation-memory growth with recurrent depth, but it is still an approximation: early recurrent computations receive no exact temporal credit assignment.

Deep supervision

A sample can run for several segments. Every segment decodes an answer, incurs the supervised loss, and performs an optimizer update. The hidden state is then detached and reused. This makes intermediate computations directly predictive and supplies frequent learning signals without supervising an explicit reasoning trace.

Adaptive computation time (ACT)

A two-output Q head on the high state estimates halt and continue. Halting receives a binary reward for exact output correctness; continuing bootstraps from the next segment’s Q values. Exploration sometimes imposes a random minimum number of segments.

Training

Stop when maximum segments is reached or halt value exceeds continue value after the sampled minimum. Halt/continue BCE is added to sequence loss.

Official batched evaluation

The implementation runs to the configured maximum for batching rather than using learned early exits. True adaptive serving therefore needs a separate evaluation path.

Combat meaning: ACT selects how long the network thinks about one legal-action decision. It neither advances the simulator nor ends the player turn.

HRM fact

Official implementation profile

The default architecture is a non-causal encoder over a fixed-length sequence. Both recurrent modules use the same Transformer-block shape; their parameters are separate.

Stablemax in the official loss

The implementation maps nonnegative logits with s(x)=x+1 and negative logits with approximately s(x)=1/(1−x), normalizes these positive values, and takes their logarithm for cross-entropy. The paper uses it for small-sample generalization. Combat experiments should compare stablemax and ordinary softmax under the same seeds.

Operational notes from the official README

The repository expects PyTorch/CUDA and FlashAttention, integrates Weights & Biases, and describes single-GPU and eight-GPU recipes. It warns that 1K-sample experiments can vary by roughly two accuracy points and that late Sudoku training can overfit or destabilize Q-learning, recommending early stopping near full training accuracy.

The paper reports near-perfect exact solutions on difficult Sudoku and optimal 30×30 maze pathfinding from 1,000 examples, while a direct 8-layer Transformer with a matched training setup fails on those small-data tasks. It also reports that increasing the inference segment cap can improve Sudoku accuracy.

Do not transfer the headline sample-efficiency claim literally. A Sudoku example supplies 81 dense output-token labels, a maze supplies up to 900, augmentation creates many variants, and the target is deterministic and fully observed. One combat entry is interactive and branches after every action; the engine creates comparable density through suffix replay and optional counterfactual rollouts.

Recommended problem formulation

Train a receding-horizon policy. At decision state sₜ, the model reasons internally, scores only legal_actions(sₜ), selects aₜ, and lets the exact engine produce sₜ₊₁. The model may retain a recurrent planning state across decisions as an ablation, but correctness must not depend on stale hidden state after unexpected outcomes.

sₜ → serialize(sₜ) → HRM segments → scores(a ∈ Legal(sₜ)) → choose aₜ
sₜ₊₁ = Engine.step(sₜ, aₜ) → repeat until terminal

Combat proposal

A combat-native HRM

Use HRM as the state encoder and latent deliberation core. Replace the grid decoder with structured action scoring and a required terminal-progress head.

Intended high state

Slow fight plan

  • boss phase and upcoming transition window;
  • damage race and survivability budget;
  • power setup versus immediate tempo;
  • orb release/protection schedule;
  • next-turn resource and draw expectations.
Intended low state

Fast turn tactics

  • card order, costs, X-cost allocation, and targets;
  • lethal/block arithmetic and overkill;
  • orb channel/evoke sequencing;
  • potion timing;
  • legality and exact post-action consequences.

These roles are desired representations, not guaranteed emergent behavior. Auxiliary probes can measure whether the separation appears; auxiliary losses can encourage it only after a plain model baseline exists.

State-token contract

Serialize entities as typed groups, preserve meaningful order, and attach numeric features through bucket tokens or projected scalar features. A practical sequence is:

[CLS]
[RUN] ascension act floor character max_hp hp gold
[TURN] turn energy block cards_played stance/phase bookkeeping
[PLAYER_POWERS] (power_id amount ...)
[ORBS] capacity focus [SLOT 0 type passive evoke ...] ...
[HAND] [CARD 0 id upgrade cost flags ...] ...
[DRAW] aggregate or ordered observable cards
[DISCARD] card multiset / ordered list when relevant
[EXHAUST] card multiset
[ENEMIES] [ENEMY 0 id hp block intent powers phase ...] ...
[RELICS] (relic_id counter ...)
[POTIONS] (slot potion_id usable ...)
[LEGAL] structured encodings of every legal action
[END]

Observable-policy track

Include only information available to a real player or explicitly derived from it. This is the fair deployment target.

Engine-oracle track

Include RNG/private bookkeeping only as a separate upper-bound experiment. Never mix oracle examples into the observable-policy evaluation.

Legal-action head

The engine already exposes a state-dependent Game::legal_actions() set containing card plays with optional targets, EndTurn, and potion operations. Encode each candidate action, cross-attend it to the final high state, and emit one scalar per candidate:

eₐ = ActionEncoder(type, card/slot, target, cost, local features)
logit(a) = MLP([pool(zH); eₐ; interaction(pool(zH), eₐ)])
π(a | s) = softmax(logit(a)) over a ∈ Legal(s) only
  • Never learn legality as the only guardrail; use the exact engine mask.
  • Prefer semantic action identities over the transient list index. Hand and enemy indices remain features because they identify current entities.
  • If equivalent actions occur, canonicalize them or allow a set of acceptable labels.
  • ACT halt/continue logits come from a separate head and cannot enter this action softmax.

Terminal progress score

Rollouts receive a piecewise terminal score that measures actual progress and remains informative when a candidate line dies.

Combat won

Player HP delta

ΔHPplayer = HPend − HPentry

Prefer the winning line that preserves more player HP; values closer to zero are better when no healing exceeds entry HP.

ELSE
Combat lost

Monster HP delta

ΔHPmonsters = M(entry) − M(end)

Prefer the failed line that removed more phase-normalized encounter HP, so training/search still sees progress toward a kill.

Ordering rule: compare terminal outcome first (a win outranks a loss), then compare the applicable HP delta within that outcome. This avoids a high-damage loss outranking a win while retaining dense ranking among failed continuations.

Here M(s) is total remaining monster HP across every required living or latent boss phase. Donu and Deca contribute both living HP pools; Awakened One includes its current and still-unseen form; a Time Eater heal increases remaining HP again. Defining the delta this way keeps phase transitions continuous and prevents a newly spawned form from looking like negative progress.

Use this score for teacher search, counterfactual action ranking, rollout regret, and the model’s progress head. Without the loss branch, failed continuations would have no direction of improvement.

Expansion into training examples

  1. Recreate the entry exactly from action_prefix, then verify state equality.
  2. At each suffix decision, save the serialized observation, complete semantic legal-action set, chosen expert action, boss/turn metadata, and entry puzzle ID.
  3. Apply the expert action through the engine and repeat until terminal. This turns one entry into a trajectory of supervised state/action pairs.
  4. Optionally branch alternative legal actions, continue them with HTN/search, and label each by terminal outcome plus the applicable HP delta.
  5. Store an exact serializer/schema version and engine commit with every derived shard.

Split unit: the entire entry puzzle

All decision states, counterfactual branches, augmentations, and suffix positions derived from one entry seed must remain in the same split. The implemented default is a deterministic 400 train / 50 validation / 50 test split, proportionally stratified by boss. Entry-HP stratification remains a useful later ablation.

Trajectory leakage is a split error, not an objection to winner-only entries. Randomly splitting individual turns would let the model train on earlier states and test on later states from the same deterministic fight. Splitting whole puzzles measures transfer to unseen boss entries.

What this corpus is for

  • Training a conditional solver for complete, known-good Act 3 boss-entry puzzles.
  • Testing multi-turn planning, phase timing, action order, and HP preservation.
  • Measuring generalization across unseen seeds and boss-state configurations.

Failed model rollouts supply graded monster-HP progress, while successful rollouts supply player-HP preservation. Both are action-quality signals produced by playing the puzzle.

Combat proposal

Training objectives

Use expert action imitation to anchor the policy and train the piecewise terminal-progress score alongside it. The score is required for rollout improvement: it distinguishes HP-preserving wins and gives every failed line a direction through monster damage.

Ltotal = Lpolicy + λscore·Lprogress + λrank·Lrank + λact·Lhalt + λaux·Laux
TermTargetInitial status
LpolicyCross-entropy over the expert action within the exact legal set. Support multiple acceptable actions when search scores tie within tolerance.Required.
LprogressPredict outcome-conditional terminal HP delta: player HP delta on wins, monster HP delta on losses.Required; source targets from expert and branched/model rollouts.
LrankRank counterfactual actions by outcome first, then applicable HP delta.Requires branch rollouts.
LhaltChoose whether another latent segment materially changes or improves the action prediction.Defer until fixed-compute HRM works.
LauxOptional boss phase, incoming damage, next-turn energy, orb events, or exact successor features.Diagnostic first; train only with ablation.

ACT target for combat

The original binary “entire output exactly correct” target is awkward when actions can be near-equivalent. A combat-native halt reward should use teacher agreement or regret:

halt_correct(m) = 1 if chosen action at segment m is expert-acceptable
or: halt_utility(m) = −regret(chosen action, best action) − compute_cost·m

Implement fixed segment counts first. ACT adds a Q-learning subsystem that can obscure whether gains came from hierarchy or merely more compute.

Teacher choices versus terminal score

The winning suffix supplies the primary action label. The piecewise terminal score resolves candidate continuations and gives failed model rollouts a direction of improvement. A sparse terminal win bit alone cannot express that progress.

Implemented · default experiment

One command, not twenty parameters

The dedicated sts-hrm-train binary owns the standard corpus, exact replay expansion, tensor cache, model configuration, device selection, ten-minute budget, evaluation, and artifact names. The normal interface is:

cargo run --release --bin sts-hrm-train

With no arguments it uses the checked-in 500-puzzle Defect A0 Act 3 boss corpus, replays every winning suffix through the engine, constructs a deterministic boss-stratified 400/50/50 puzzle split, selects CUDA when available, trains for 600 wall-clock seconds, and writes under artifacts/hrm. It uses an existing training environment when possible and otherwise provisions one through uv, then exports an FP16 ONNX graph and runtime manifest for trainer-neutral Rust inference.

Research protocol

Experiment ladder

Every rung answers one question. Use identical puzzle splits, state serializer, legal actions, training examples, model-selection rules, and reporting seeds.

  1. Data integrity baseline. Replay all 500 entries and suffixes, round-trip every action encoding, and prove that every target action appears exactly in the legal set.
  2. Direct policy baseline. Non-causal Transformer state encoder with one forward pass and the same legal-action head.
  3. Single recurrent baseline. One recurrent module with the same executed layer count and approximate parameter budget as HRM.
  4. Fixed-compute HRM. H/L modules, detached one-step gradients, and a constant segment count. This tests hierarchy without ACT.
  5. Gradient ablation. Compare one-step approximation with short truncated BPTT under equal memory or wall-clock budget.
  6. Progress/ranking heads. Add terminal HP-delta prediction and counterfactual ranking. Measure policy and rollout changes separately.
  7. Adaptive compute. Add ACT only after the fixed model is stable. Compare quality at equal mean and maximum executed FLOPs.
  8. Policy improvement. Roll the model through training puzzles, ask HTN/search to relabel disagreements or failures, and retrain without changing the held-out test set.

Fair comparison rules

  • Report parameters, peak memory, executed layers/FLOPs, segments, examples, and wall-clock time.
  • Match direct baseline depth to actual HRM execution, not just stored layer count.
  • Use at least three training seeds; the official repo itself notes small-data variance.
  • Freeze the 50-puzzle test split before tuning.
  • Select checkpoints using validation rollouts, never test action accuracy.
  • Keep boss mixture and entry-HP distribution visible in every result.

Go / no-go threshold

Continue investing in HRM only if fixed-compute HRM improves held-out puzzle rollouts over both baselines at a defensible compute budget. Action accuracy alone is not enough. ACT is valuable only if it traces a better score–compute frontier than fixed segment counts.

Failure analysis

Known traps

Seed memorization

Raw seed, action prefix, exact RNG state, or stable record IDs may identify a training trajectory. Exclude direct identifiers, split entire entry puzzles, and label any exact-RNG experiment as an engine-oracle solver rather than an observable policy.

Action-index aliasing

The same list index means different cards or targets in different states. Encode semantic actions, using list position only to dispatch the selected candidate.

Oracle leakage

Full serialized engine state may expose information a deployed agent should not know. Maintain separate observable and oracle schemas.

Teacher determinism

One suffix can hide alternate wins. Counterfactual search or near-tie labels prevent punishing equivalent strong moves.

Compute-confounded gains

HRM can execute far more layers than a nominal “8-layer baseline.” Compare actual execution and wall-clock cost.

Detached-credit failure

One-step gradients may not teach consequences requiring many recurrent updates. BPTT and direct-depth ablations are mandatory.

ACT instability

The official Q-learning design has neither replay buffer nor target network. Fixed-compute training should establish a stable baseline first.

Progress-score sign errors

Player HP preservation and monster damage use different semantics. Centralize comparison logic and test win-over-loss ordering.

Stale plan state

A hidden plan carried across engine actions may assume a branch that did not occur. Re-encoding full state each decision is the safe baseline.

Overfitting 500 puzzles

Track train/validation rollout gaps, use puzzle-level splits, early stopping, and boss-stratified learning curves.

Claims this experiment must not make

  • That brain inspiration explains performance.
  • That latent states implement symbolic search without causal evidence.
  • That 500 entry puzzles imply broad full-run or A20 generalization.
  • That a model matching an expert action has found the only winning action.
  • That more segment compute is architectural improvement unless baselines receive equal compute.

Implementation handoff

Minimal build sequence

  1. Freeze semantics. Implement one tested terminal comparator: outcome first, then player HP delta for wins or monster HP delta for losses.
  2. Build the extractor. Replay all 500 prefixes and suffixes and emit versioned per-decision examples grouped by puzzle.
  3. Build semantic candidate actions. Round-trip every Action variant and assert exact membership in legal_actions().
  4. Define observation v1. Start with full combat-relevant observable state; log excluded private fields explicitly.
  5. Train the direct baseline. Establish data correctness and rollout evaluation before recurrence.
  6. Train single recurrence. Establish whether iterative refinement itself helps.
  7. Train fixed HRM. Port the pinned H/L schedule and one-step gradient faithfully; keep action head combat-native.
  8. Add counterfactuals. Branch difficult or disagreed actions and label terminal progress with exact engine rollouts.
  9. Add ACT last. Optimize adaptive compute only after a fixed segment count produces reliable held-out wins.

Integrity tests before any long run

  • All 500 source suffixes replay to a win under the pinned engine.
  • No puzzle ID occurs in more than one split.
  • No raw seed, prefix hash, source hash, or stable record ID enters model features; exact RNG state is allowed only in an explicitly labeled engine-oracle schema.
  • Every expert target is present in the reconstructed legal-action set.
  • Action encode/decode is bijective for every observed combat action.
  • Any win compares above any loss.
  • Among wins, greater player HP preservation ranks higher.
  • Among losses, greater monster HP removed ranks higher.
  • ACT halt never dispatches EndTurn.
  • Observable and oracle schemas cannot be mixed silently.

Research questions worth answering

  1. Does hierarchy improve full-combat win rate beyond a compute-matched recurrent Transformer?
  2. Does the high state retain boss-phase and multi-turn resource information longer than the low state?
  3. Does terminal HP-delta ranking improve recovery from off-expert states?
  4. How many entry puzzles are needed before held-out rollout performance saturates?
  5. Does adaptive compute allocate more segments to phase transitions, lethal searches, and dense legal-action states?
  6. Can a model trained on the three Act 3 bosses transfer to elites or A20 without sacrificing the scoped solver?
